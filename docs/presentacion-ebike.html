// Módulo 01: Contexto de Negocio

¿Qué problema resuelve este sistema?

e-Bike no es solo una página web; es un ecosistema operativo completo para la gestión de bicicletas eléctricas compartidas en Medellín.

01

Para el Ciudadano (Cliente)

Explora estaciones en tiempo real, desbloquea una bicicleta mediante código, monitorea su tiempo de viaje acumulado y realiza devoluciones autónomas con costo transparente.

02

Para el Operador de Campo

Monitorea niveles de batería en cada anclaje, reemplaza baterías descargadas, registra mantenimientos preventivos/correctivos y balancea la flota entre estaciones.

03

Para el Administrador

Supervisa el 100% de los alquileres en vivo, resuelve incidencias, ajusta las tarifas del servicio en COP, gestiona usuarios y revisa el log de auditoría para trazabilidad.

// Módulo 02: Concepto Fundamental

¿Por qué decimos que Next.js es Full-Stack?

Es común pensar que Next.js es solo React o solo frontend. En realidad, unifica el cliente y el servidor en un solo proyecto ejecutable.

Lado Cliente (Frontend)

Componentes interactivos de React 19 ("use client") con estado, hooks de TanStack Query, formularios reactivos, mapas interactivos y diseño con Tailwind CSS v4.

Lado Servidor (Backend)

Ejecuta código seguro en Node.js mediante Server Actions ("use server"). Se conecta directamente a la base de datos PostgreSQL mediante Drizzle ORM, valida sesiones criptográficas con Better-Auth y nunca expone contraseñas ni tokens al navegador.

⚡ Ventaja Clave: No requerimos crear un backend separado en Express ni configurar CORS. Todo se comunica de forma tipada y segura dentro del mismo ciclo de vida.
// FLUJO DE UN SERVER ACTION EN NEXT.JS 16
[Navegador del Usuario] → Envía Click "Devolver Bici"
↓ returnRentalAction(idAlquiler, idEstacion)
Node.js Server Environment:
1. Verifica cookie de sesión (Better-Auth)
2. Valida input con Zod v4
3. Consulta tabla 'tarifas' en PostgreSQL
4. Inicia Transacción SQL con Drizzle ORM
5. Retorna solo el DTO seguro al cliente
[Navegador se actualiza] ← Responde: "Costo $4.100 COP"

// Módulo 03: Arquitectura Tecnológica

Herramientas y Librerías del Proyecto

Cada tecnología fue seleccionada para maximizar la velocidad, la seguridad de tipos y la mantenibilidad a largo plazo.

Next.js 16.3.6 App Router

Compilación ultra-rápida con Turbopack, renderizado híbrido en servidor, rutas dinámicas y ejecución nativa de Server Actions.

React 19 React Compiler

Aprovecha el compilador automático de React 19 para memoización reactiva sin sobrecarga manual de useMemo ni useCallback innecesarios.

PostgreSQL + Drizzle v2 ORM Typesafe

ORM tipo-seguro sin latencia. Utiliza defineRelations v2, consultas SQL transaccionales y migrador automático sin generar código inflado.

Better-Auth 1.7 Auth + Admin Plugin

Sistema moderno de autenticación con hashing Scrypt, revocación de sesiones en base de datos, protección anti-fuerza bruta y plugins administrativos.

Tailwind CSS v4 CSS-First Engine

La última generación de Tailwind con motor nativo en Rust, variables CSS modernas, dark mode fluido y sin necesidad de archivo de configuración pesado.

Zod v4 + TanStack Query Validación & Cache

Validación estricta de payloads en servidor con Zod v4, combinada con sincronización y revalidación reactiva de estado asíncrono en el cliente.

// Módulo 04: Modelo Relacional

Estructura de Base de Datos (PostgreSQL)

Diseño robusto de 14 entidades en 3ra forma normal con claves foráneas, enums nativos de PostgreSQL y comprobaciones lógicas (CHECK constraints).

1. users & sessions Auth & RBAC

Controla identidades, passwords hasheados, tokens de sesión y el enum userRoleEnum ('admin', 'operador', 'cliente').

2. estaciones Infraestructura

Puntos geográficos con capacidad física, anclajes magnéticos, coordenadas lat/lng y estado ('operativa', 'en_mantenimiento').

3. bicicletas Flota Activa

Flota eléctrica con código QR único, número de serie, kilometraje, nivel de batería y estación actual asignada.

4. baterias Componentes

Monitoreo individual de celdas de litio, ciclos de carga acumulados, temperatura operativa (°C) y estado de degradación.

5. alquileres Operación Core

Registra el ciclo de viaje: usuario, bici, estación origen, estación destino, fecha inicio, fecha fin, estado y costo total en COP.

6. tarifas Precios Dinámicos

Tabla independiente que almacena la tarifa activa: tarifaBase ($2.000 COP) y tarifaMinuto ($300 COP).

7. mantenimientos Taller & Campo

Órdenes de trabajo preventivas y correctivas asociadas a bicicletas y operadores técnicos responsables.

8. registros_energia Sostenibilidad

Consumo de kWh por estación, costo unitario de energía, facturación calculada y alertas automáticas de anomalías de red.

9. auditorias Trazabilidad Total

Bitácora inmutable en JSONB de cambios críticos (quién cambió el estado de una bicicleta, suspensiones de cuentas o cierres forzados).

1. Actions (Server-Side)

Contienen la lógica de negocio pura. Verifican la identidad y el rol con getSessionDetails(), ejecutan transacciones atómicas en PostgreSQL y retornan una respuesta estandarizada IGeneralResponse<T>.

2. Validations (Zod v4)

Impiden la inyección de datos corruptos o campos maliciosos mediante esquemas estrictos (.strict()). Si el frontend envía un campo inesperado, el servidor lo rechaza de inmediato.

3. Queries (TanStack Query)

Manejan la caché del navegador. Si un usuario cambia de página y regresa, los datos se muestran al instante mientras se refrescan en segundo plano con claves normalizadas (Query Keys).

4. Barrel Exports (index.ts)

Cada subcarpeta expone su interfaz pública mediante un archivo index.ts, evitando importaciones acopladas a rutas profundas.

// Módulo 06: Casos Prácticos

Lógica de Cálculo y Retorno de Viajes

Cómo el sistema calcula en tiempo real lo que paga un usuario y cómo el administrador puede intervenir en caso de incidencias.

// FÓRMULA OFICIAL DE COBRO EN COP
Costo = Tarifa Base + (Minutos × Tarifa Minuto)
Tarifa Base: $2.000 COP (Desbloqueo)
Tarifa por Minuto: $300 COP (Uso activo)
Regla de Redondeo: Math.ceil() (Mínimo 1 minuto)
PASO 1
Reserva / Desbloqueo

El cliente elige estación y bici. El estado de la bicicleta pasa a 'en_uso' y se genera el alquiler con fechaInicio = NOW().

PASO 2
Viaje en Curso

El portal muestra un temporizador reactivo. En el panel administrativo, el alquiler figura con badge verde En curso.

PASO 3
Devolución en Estación

El cliente ancla la bici en una estación de destino. El servidor calcula los minutos exactos con la tarifa activa y cierra el ciclo.

PASO 4
Historial & Finiquito

Se registran fecha fin y costo final. En el historial de ambos paneles se visualizan las columnas de Fecha Inicio y Fecha Fin.

Guía Rápida para Responder Preguntas del Profesor

Puntos clave que debes dominar durante la exposición oral.

¿Por qué usamos Drizzle ORM en lugar de Prisma o SQL nativo? ↓

Prisma genera un binario pesado (Rust engine) y tiene problemas de rendimiento en entornos serverless. SQL nativo no nos da autocompletado en TypeScript. Drizzle es casi tan rápido como SQL nativo pero nos garantiza que si renombramos una columna en la base de datos, TypeScript nos marcará error en todos los lugares donde la usamos antes de compilar.

¿Cómo garantizamos que un usuario no cierre el alquiler de otro? ↓

En ningún momento confiamos en el cliente. En returnRentalAction obtenemos la sesión activa desde la cookie del navegador (getSessionDetails()). En la consulta SQL forzamos la condición and(eq(alquiler.idAlquiler, id), eq(alquiler.idUsuario, currentUser.id)). Si un cliente malicioso envía el ID de otro usuario, la base de datos no retorna filas y la operación se cancela de inmediato.

¿Cómo se maneja la consistencia si el servidor falla durante la entrega? ↓

Usamos Transacciones ACID en PostgreSQL con drizzleDB.transaction(async (tx) => ...). Si se actualiza el alquiler pero falla la liberación de la bicicleta, la transacción hace Rollback completo y nada queda corrupto a la mitad.

¿Cómo se protegen los roles de usuario (RBAC)? ↓

Tenemos una doble barrera: a nivel visual y de navegación, el layout privado y el sidebar filtran las opciones según el rol de la sesión. Pero lo más importante: a nivel de Server Action, cada acción administrativa revalida hasRequiredRole(userRole, ADMIN_ROLES). Si alguien intenta invocar la Server Action por POST directo sin privilegios, recibe un 403 Forbidden.
